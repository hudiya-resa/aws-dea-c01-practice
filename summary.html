Domain 1: Data Ingestion and Transformation

How to get data into AWS, turn it into something useful, orchestrate the pipeline flow, and the programming concepts behind it.

Domain 1 introduction

Ingestion and integration

  • Data ingestion: moving data from point A to point B.
  • Data integration: combining several sources into a new dataset (example: advertising plus web analytics into a user profile). This is part of transformation.
  • Ways to ingest: direct database connection, change data capture, API, message queue, event streaming, file export, object storage (Amazon S3).
  • Ways to transform: queries, modeling, transformations.

Four task statements

  • 1.1 Perform data ingestion: throughput, latency, streaming and batch.
  • 1.2 Transform and process data: ETL pipeline, volume, velocity, variety, distributed computing.
  • 1.3 Orchestrate data pipelines: scheduling, dependencies, event-driven, serverless workflow.
  • 1.4 Apply programming concepts: CI/CD, SQL, infrastructure as code, data structures (graph, tree).

Lesson 1: Perform data ingestion

Lifecycle and core concepts

  • Stages: generation, storage, ingestion, transformation, serving.
  • Generation is the source system. The data engineer uses its data but does not control the system.
  • Two big concepts: batch vs streaming, push vs pull.
  • Flow: producer (database, mobile, application) to ingestion tool to consumer (EC2, AWS database, Lambda).

Replayability

  • The pipeline can reprocess data when it fails or when the logic changes.
  • Design event-driven: Amazon S3, Amazon Kinesis, Amazon EventBridge fire events when new data arrives.
  • Test idempotency: the same data processed many times with nothing lost or duplicated.
  • Add checkpoints so processing can resume from the last successful point.
  • Keep raw or intermediate data in S3 (versioning, compliance, replay). Deploy with CloudFormation or AWS CDK.

S3, Athena, Redshift examples

  • TSV files in S3: register them in Amazon Athena, then run ad hoc SQL queries. Convert to Parquet for faster queries.
  • BI team needs a warehouse: load into Amazon Redshift, join with S3 data through Redshift Spectrum.
  • Athena table stays updated as new data arrives: AWS Glue crawler.
  • COPY is slow from one large gzip file: split it into smaller files, a multiple of the number of slices. COPY uses MPP and loads in parallel. Set the distribution key.

Service per use case

  • Data lake: S3, no schema up front. Warehouse or lakehouse: Redshift and Redshift Spectrum.
  • Big data processing: Amazon EMR. Real-time analytics: Kinesis and Amazon MSK.
  • Operational analytics (application monitoring, logs, clickstream) near real time: Amazon OpenSearch Service.
  • Transactional (small data, fast): DynamoDB and RDS. AWS DMS uses the transaction log for CDC, engine migration (Oracle to Aurora), and ongoing replication to S3.

Five Vs of data

  • Variety: types of data. Volume: size and growth, watch the record size limit per service.
  • Velocity: tell real time from near real time. Services for spiky traffic: Kinesis, MSK, OpenSearch, Lambda.
  • Veracity: quality and completeness (example: an IoT sensor goes down).
  • Value: the most important V. Processing data that has no value is wasted money.

Kinesis family

  • Streaming: many small events (around 1 KB), hot data, bounded by time or event count.
  • Kinesis Data Firehose: buffers for a set period, then writes to S3, Redshift, OpenSearch Service. Note: now called Amazon Data Firehose.
  • Kinesis Data Streams: real time, low latency, custom applications.
  • Amazon Managed Service for Apache Flink (formerly Kinesis Data Analytics): stream analytics with SQL or Flink.
  • Kinesis Video Streams: video, audio, thermal imagery, radar. Kinesis Agent: reads files and sends them to Streams or Firehose.
  • Hot shard (write throttled): UpdateShardCount to add shards, random partition key, set alarms on metrics.

Other ingestion services and batch

  • MSK to replace an existing Kafka cluster, you pay for the cluster even when idle. Kinesis is serverless, you pay for throughput.
  • Amazon AppFlow: from SaaS. AWS Transfer Family: FTP and SFTP to S3. AWS DataSync: on-premises NFS and SMB. Snow Family: very large data.
  • Batch: large payloads, scheduled hourly up to weekly, for cold data. EMR (Spark plus JDBC) or AWS Glue (fully managed ETL, JDBC, Glue Studio).
  • Stateful: ElastiCache for Redis, RDS. Stateless: Lambda, API Gateway, S3.

Lesson 2: Transform and process data

Modeling, OLTP, OLAP

  • Know conceptual, logical, physical models, normalization, and data vault.
  • OLTP: real-time transactions, current state, small storage, fast response (orders, payments).
  • OLAP: analysis and reporting, history, star or snowflake schema, storage from terabytes to petabytes.
  • Transformation: change data types, standardize formats, drop bad data, aggregate for reports or ML features.
  • Transformation can happen during ingestion. Example: Firehose writing Parquet.

Processing services

  • Cloud computing: Lambda, EMR, Glue, Redshift. Distributed: EMR, AWS Batch, Step Functions.
  • Lambda for light validation and transforms, for example on each CSV file that lands in S3.
  • AWS Glue: serverless, Python or Spark engine, data in S3.
  • Glue Data Catalog gives a logical view over DMS output files (one prefix per table). Query through Athena or use in EMR and Glue ETL code.
  • Glue crawler infers the schema and fills the catalog automatically.

Glue vs EMR vs Flink

  • EMR: full Hadoop (Spark, Hive, Hudi, HBase, Presto, Pig), more capable than Glue, but not fully managed.
  • Spark on EMR: create a cluster, set memory and executor cores, submit jobs with spark-submit, scale up or down.
  • Glue: fully managed, enough for cleansing, enrichment, data movement.
  • Flink: basic SQL transformations. Complex transformations move to EMR or Glue.

Architecture examples

  • Secure IoT near real time: Firehose to S3, Lambda removes sensitive data before it is stored.
  • Web logs on EC2: Kinesis Agent to Firehose, to S3 and to Flink, then a second Firehose to OpenSearch, visualized in Kibana.
  • Reduce Redshift load when joining history in S3: Redshift Spectrum external table.
  • Enrich CloudWatch Logs with DynamoDB: CloudWatch Logs subscription to Firehose, Lambda to enrich, destination S3.

Troubleshooting

  • Check service logs, data quality at each stage, then mapping, filter, and aggregation logic.
  • Glue has a development mode and a debugging mode. Debug with a small dataset.
  • Optimization: partitioning, parallelism, memory and executor tuning, caching.
  • Incremental processing for new data only. Retry for temporary issues.
  • Unit, integration, and end-to-end tests in staging.

Connectivity and data APIs

  • JDBC: Java API. Set up the driver, open the port in the security group inbound rules, URL holds host, port, database name.
  • ODBC: install the driver, create a DSN, the application connects through the DSN.
  • RDS, Aurora, Redshift reduce manual JDBC or ODBC setup.
  • Data API: API Gateway (auth, rate limiting, caching, versioning) plus Lambda. Security: IAM, Certificate Manager, API keys, OAuth.
  • Cache: ElastiCache or API Gateway cache. Monitoring: CloudWatch. CI/CD: CodePipeline and CodeBuild.

Lesson 3: Orchestrate data pipelines

Pipeline concepts

  • Know the architectures: data warehouse, data lake, lakehouse, Lambda, Kappa, data mesh. Reference: Well-Architected Framework, six pillars.
  • Pipeline: a set of tasks in a defined order, sequential or parallel. The order is called a workflow.
  • Serverless orchestration: Step Functions and Lambda.
  • Airflow requires a DAG, Step Functions does not.
  • Correction Notice: the video says "Directed Acrylic Graph". The correct term is Directed Acyclic Graph, a directed graph with no cycles.
  • Many small files as one batch: send a manifest file, S3 event notification only for the "manifest" prefix, then check each file. Still event-driven.

Failures and retries

  • Data quality (receiving JSON when CSV is expected) and code errors: hard failure.
  • Endpoint errors: a temporary network issue is a soft failure, wrong permissions is a hard failure.
  • Dependency errors: within or between pipelines.
  • Step Functions: interval 10 seconds, backoff rate 1.5, waits of 10, 15, 22.5 seconds.
  • Alerts: Amazon SNS topic with an email subscription.

Service choices

  • Serverless: AWS Data Pipeline and Step Functions. Managed open source: Amazon MWAA. Specialized: Glue workflows.
  • Data Pipeline: scheduled ETL between AWS and on-premises, supports on-premises JDBC. The instructor picks it for less complex environments.
  • Step Functions: visual low code or Amazon States Language (JSON), for more complex environments. Triggered by EventBridge or API.
  • Glue workflows: when the pipeline is purely Glue components, use triggers. Other services through a Glue Python shell job with Boto3.
  • MWAA: managed Airflow, DAGs written in Python.
  • Note: AWS Data Pipeline has been in maintenance mode since 2024. CloudWatch Events is now part of EventBridge.

Pipeline examples

  • Raw zone from Firehose, DMS, DataSync. S3 triggers a Lambda that runs a crawler.
  • A CloudWatch Events rule triggers Glue ETL to Parquet in the processed zone, then SNS sends an email.
  • Step Functions with EMR: Lambda submits a Spark job, waits, checks status, goes to success or failure.
  • A Choice state reads the job status. A Catch statement runs a notification Lambda on error.
  • Athena over data in two Regions: a Glue crawler in one Region catalogs all Regions.

Best practices

  • Distributed processing, auto scaling, partitioning.
  • Fault-tolerant storage: S3 or EFS. Backup: S3 or AWS Backup.
  • CloudWatch alarms. Retries with Step Functions or Glue workflows.
  • Data validation, testing, version control, CI/CD.

Lesson 4: Apply programming concepts

SQL vs Spark

  • SQL: standard and widely known. Spark: more flexible for complex processing with latency and throughput requirements.
  • Spark on AWS: Glue (serverless), EMR, ECS or EKS, partners such as Databricks.
  • Target in Redshift means ELT, use SQL.
  • Transform in Spark then load into the warehouse means ETL, the warehouse load stays focused on user queries.
  • Redshift: the parser and optimizer build a query plan, the execution engine sends code to the compute nodes.

ETL tools

  • EMR: Hadoop, Spark, HBase, Presto, YARN, Tez, Pig, one to thousands of nodes.
  • Data Pipeline: data nodes and activities (S3 data node, Hive activity on EMR, Redshift copy activity).
  • Glue Studio: visual SQL-based transformations on the Spark engine for users without Spark skills. Glue DataBrew: transformations on a set of files.
  • Athena column names: alphanumeric characters and underscores only (/var/log becomes var_log).

Runtime optimization

  • Parallel and batch processing.
  • Parquet or ORC, compression, partitions by date or Region.
  • Filter data early, incremental processing.
  • Tune memory and parallelism, monitor with CloudWatch.

IaC, CI/CD, Lambda

  • CloudFormation or CDK for repeatable deployments. AWS SAM for Lambda, Step Functions, DynamoDB.
  • Templates in CodeCommit or GitHub, CI/CD runs on each commit. Note: CodeCommit has not accepted new customers since 2024.
  • Lambda: set memory, concurrency limit, timeout, retries. Asynchronous invocation when no immediate response is needed.
  • Provisioned concurrency to prewarm. Lambda in a VPC adds latency.

Data structures and algorithms

  • Data structures: relational, NoSQL, warehouse, distributed file system, message queue, tree, hash table.
  • An algorithm built for one data structure becomes inefficient on another. Large sorts: Quicksort or Merge Sort.
  • Example: large customer data in HDFS on EMR, processed with MapReduce.
  • Data lost in a Kinesis Java consumer: idempotent processing and a shard iterator at the position before the error.

Key numbers and limits

  • Example streaming payload: around 1 KB per event.
  • Number of files for Redshift COPY: a multiple of the number of slices.
  • Step Functions retry: interval 10 seconds, backoff 1.5, waits of 10, 15, 22.5 seconds.
  • Batch: hourly, daily, weekly.
  • OLAP: terabytes to petabytes.
  • Well-Architected: six pillars. Five Vs of data. Five lifecycle stages.
  • Kinesis Data Streams capacity is counted per shard.
  • Athena column names: alphanumeric characters and underscores only.

Exam traps

  • Data Streams (real time, custom applications) vs Firehose (buffered, near real time, straight to the destination).
  • Real time vs near real time, read the keywords.
  • Kinesis vs MSK: a new solution means Kinesis, replacing existing Kafka means MSK.
  • Glue (fully managed) vs EMR (more complete, you manage the cluster).
  • Flink is only for basic SQL transformations.
  • DataSync vs Transfer Family vs Snow Family vs AppFlow: tell them apart by protocol and source.
  • A hard failure is not fixed by retrying. A soft failure can be.
  • Triggering only on the manifest file still counts as event-driven.
  • Glue workflows only fit when the pipeline is purely Glue.
  • Stateful (ElastiCache, RDS) vs stateless (Lambda, API Gateway, S3).

Domain 2: Data Store Management

Choosing a data store, building a data catalog, managing the data lifecycle, and designing data models and schema evolution.

Domain 2 introduction

What the domain covers

  • Four task statements: 2.1 choose a data store, 2.2 data cataloging systems, 2.3 lifecycle of data, 2.4 data models and schema evolution.
  • Storage is the third stage of the data engineering lifecycle. Data is stored many times while it moves through the pipeline.
  • First step in choosing storage: understand the use case, how data is stored, and how data is retrieved.
  • 2.3 covers hot and cold data, cost optimization, deleting data for business and legal needs, retention, archiving, resiliency.

Lesson 1: Choose a data store

Three basic storage types

  • Amazon S3: object storage, highly available, scalable, durable. For static content, backup, media, and as the base storage of a data lake.
  • Amazon EFS: fully managed file storage shared by many EC2 instances.
  • Other file storage: FSx for Windows File Server, FSx for Lustre, FSx for NetApp ONTAP.
  • Amazon EBS: persistent block storage attached to EC2. For databases and transactional apps that need low latency.

Databases and warehouses

  • Amazon RDS: managed relational database (MySQL, PostgreSQL, Oracle, SQL Server, and others).
  • DynamoDB: managed NoSQL, single-digit millisecond latency at any scale. For real-time, gaming, IoT, dynamic scaling.
  • Note: the course says DynamoDB supports graph, memory, and search. In practice DynamoDB is a key-value and document database.
  • Amazon Redshift: petabyte-scale data warehouse for analytics and BI, can also handle large volumes of semi-structured and unstructured data.
  • AWS Lake Formation: build, secure, and manage a data lake. Can crawl, catalog, and prepare data.

Factors and example choices

  • Performance factors: IOPS, scalability, durability, data access pattern.
  • Highly parallel file system for HPC, analytics, large-scale ML: FSx for Lustre.
  • In-memory caching, session storage, real-time analytics: ElastiCache.
  • Redshift fits 30 TB of data with many aggregated queries and complex joins that use only some columns. Reasons: columnar storage (less I/O), compression, parallel processing, and SQL JOIN support.

Migration and data access

  • The COPY command loads data files into a Redshift table, for example from S3 or EMR. COPY converts strings to the data type of the target column.
  • If you need other conversions, or the default conversion fails, set it with COPY parameters.
  • RDS data: the latest 3 months are used for analytics, older data is joined now and then. Solution: move old data to S3, run a daily job from RDS to Redshift, join both with Redshift Spectrum.
  • Petabytes of key-value data, direct access, SQL-like interface: Hive on EMR, store in DynamoDB.
  • EMR for short jobs: start and stop the cluster, pay per second. Long workloads: highly available cluster with auto scaling.

Preventing unauthorized access (Redshift and RDS)

  • IAM for access to clusters and resources, policies by role.
  • Security groups, encryption, and keys in AWS KMS.
  • Parameter groups for database parameters, including locking to control concurrency.
  • Database auditing, plus a regular schedule to review access logs and audit trails.

Lesson 2: Understand data cataloging systems

What a data catalog is

  • Metadata repository: location, description or schema, and runtime metrics of the data.
  • Used for federated queries and ETL when data is spread across many locations.
  • AWS Glue Data Catalog holds references to the sources and targets of ETL jobs. One metadata table represents one data store.
  • Usually filled by a crawler, but there are other ways to add metadata tables.
  • Athena uses the catalog to know the S3 location, file format (Parquet, CSV), and partitions.

Lake Formation and cross-account

  • Glue stores business attributes as key-value tags at the table level. Lake Formation supports key-value properties at the column level.
  • Lake Formation controls permissions at the database, table, and column level.
  • Case with 4 AWS accounts, each business unit can access only its own data: data lake storage in each account, catalog in a central account with Lake Formation.
  • Then update the S3 bucket policy with the Lake Formation service-linked role, and use Lake Formation permissions for specific access.
  • Users and Glue ETL jobs can join tables across accounts with table-level and column-level protection.

Keeping the catalog up to date

  • Run the Glue crawler after new data arrives.
  • New job in production: check that the job uses the AWS Glue API to update the catalog.
  • Partition sync matters for partitioned data in S3 (date, Region, category).
  • Steps: create a Glue database, create a crawler, define the partitioning schema, run it, schedule it to match ingest frequency, query with Athena.
  • Partitions that are not detected automatically are added or changed through the Glue API.

Glue connections

  • A connection for a data source (ingest) or a data target (write).
  • S3: bucket path and inclusion/exclusion patterns. RDS: endpoint, port, credentials.
  • You can test the connection first. Connections are used by crawlers and ETL jobs.

Metadata and catalog components

  • Metadata: schema, data types, data source, timestamps, data quality metrics (accuracy, completeness, consistency), ownership and access control.
  • Catalog: tables and databases, table schema, partition info, location (S3 path, endpoint), statistics from crawling.
  • Catalog also: data lineage and dependencies, tags and labels, access control policies, integration with analytics tools.

Data classification

  • Classification: group data by sensitivity so the security controls fit.
  • IAM for access. KMS for encryption keys. VPC and security groups for isolation.
  • SCPs in AWS Organizations stop member accounts from using certain actions or services.
  • Amazon Macie uses ML to discover, classify, and protect sensitive data.

Lesson 3: Manage the lifecycle of data

Hot, warm, cold

  • Ask: how important is the data, how long is it kept, how often is it accessed.
  • New data is usually accessed more often.
  • Everything in hot storage: fast but expensive. Everything in cold: slow retrieval and possible retrieval fees.
  • Transformations create new datasets that also need managing.

Cost optimization and retention

  • S3 Lifecycle policies move data to another storage class, or delete it for business and legal needs.
  • Redshift: elastic resize to add or remove nodes and change node type.
  • Know the value of the data, how it is stored, and who accesses it. Also ask whether the data can be recreated.
  • Regulations can require a certain retention, so you need a retention policy and archiving that stays searchable.

Resiliency and availability

  • S3 automatically replicates data across multiple Availability Zones.
  • RDS Multi-AZ gives automatic failover when one AZ fails.
  • Backup: AWS Backup, automatic snapshots, or replication to another Region.
  • S3 Versioning protects objects from being deleted or overwritten.

Deleting old data

  • DynamoDB Time to Live (TTL) deletes items automatically after a given timestamp.
  • Case MSK to Redshift, queries get slower and maintenance takes longer: create a sequence of identical time series tables, one per time range.
  • Delete old data with DROP TABLE, not a large DELETE, so no VACUUM is needed.
  • Small tables per time range are better optimized for queries. If sorted by timestamp, VACUUM may not be needed.

S3 and Athena case

  • CSV in S3 Standard queried by Athena: convert with Glue ETL to a columnar format, compress, partition.
  • Lifecycle: S3 Standard to S3 Standard-IA after 6 months, then to S3 Glacier after 2 years.

Lesson 4: Design data models and schema evolution

Data modeling

  • Strict normalization does not fit varied event data well.
  • Redshift supports star schema, snowflake schema, and Kimball.
  • Inmon and data vault are possible, but need extra transformation and custom solutions.
  • Redshift Serverless with Query Editor v2: create schemas and tables, import data visually.

Spark and lineage

  • EMR runs Spark clusters on demand. spark.read for structured data from S3, spark.sparkContext.textFile for raw text.
  • Glue crawler infers the schema in S3 and creates tables in the catalog, which Spark then uses.
  • Athena for interactive SQL on S3. Comprehend for NLP on unstructured text.
  • Data lineage tracks the origin, transformations, and flow of data. Helps error tracking and debugging.
  • SageMaker ML Lineage Tracking records input data, models, hyperparameters, transformations, model artifacts, and inference data. Can be integrated with Glue and S3.

Data optimization

  • RDS: indexes on columns often used in WHERE or JOIN. DynamoDB: choose the primary key and secondary indexes to match query patterns.
  • S3: partition into logical folders, query subsets with Athena or Glue.
  • Redshift: distribution key and sort key to spread data evenly and reduce data movement.
  • Compression: gzip or bzip2 in S3, column compression encoding in Redshift. Parquet or ORC format in S3.
  • Cache: ElastiCache or CloudFront. Historical data: S3 Glacier or Glacier Deep Archive.
  • DynamoDB provisioned throughput plus auto scaling. Query tuning: RDS Performance Insights, Redshift query monitoring. Transfer: DataSync or Transfer Family.

Data types and services

  • Structured: RDS, Aurora, Redshift.
  • Semi-structured: DynamoDB, DocumentDB (MongoDB compatibility), Athena, S3.
  • Unstructured: S3, Rekognition, Transcribe, Comprehend.

Schema evolution

  • Fields added or removed, types changed (string to integer). The goal is to keep old data usable and keep backward compatibility.
  • DynamoDB: just update the application, old data without the new attributes still works.
  • RDS and Aurora are harder: use AWS DMS with minimal downtime, or stored procedures.
  • S3 data lakes use schema on read: raw data, schema applied at query time through Athena or Glue.
  • AWS Glue supports schema versioning. Avro, Parquet, ORC support schema evolution by design.
  • Note: the course calls Avro columnar. Avro is actually row-based, the columnar ones are Parquet and ORC.

Anticipating and converting schemas

  • Proactive: dead letter queue, schema registry, schema validation, versioning, backup before changes, monitoring and alerting.
  • Test a new schema: Glue, AWS Data Pipeline, or a custom script. Glue DataBrew for data profiling.
  • Note: AWS Data Pipeline is in maintenance mode and closed to new customers.
  • AWS SCT converts schemas and code between engines (data type mapping, stored procedures, indexes), with an assessment of issues.
  • AWS DMS works with SCT when migrating to RDS, Aurora, Redshift, and others.

Broken records due to schema changesdead letter queue, schema registry.

Key numbers and limits

  • 4 task statements. Storage is stage 3 of the data engineering lifecycle.
  • DynamoDB: single-digit millisecond latency.
  • Redshift is petabyte scale. Example case: 30 TB, hundreds to thousands of aggregated queries per day.
  • RDS case: the latest 3 months of data stay in the database.
  • EMR short jobs: pay per second.
  • S3 Lifecycle: Standard-IA after 6 months, Glacier after 2 years.
  • Cross-account case: 4 AWS accounts and one central data lake account.
  • Glue partition sync: 6 steps.

Exam traps

  • S3 is object, EFS is shared file, EBS is block attached to one EC2 instance. Watch for the words "shared" and "block-level".
  • EFS and FSx for Lustre are both file storage. "Highly parallel" or HPC means FSx for Lustre.
  • Redshift Spectrum queries data that stays in S3. No need to load it into the cluster.
  • Type conversion fails during COPY: the answer is COPY parameters, not a different service.
  • Glue tags are at the table level, Lake Formation goes down to the column level.
  • Deleting Redshift data: DROP TABLE beats a large DELETE because no VACUUM is needed.
  • DynamoDB TTL is for items, S3 Lifecycle is for objects. Do not mix them up.
  • Cold storage is cheap but retrieval is slow and costs money. Do not pick Glacier for data that is still queried often.
  • Macie discovers and classifies sensitive data. Access is still controlled by IAM, Lake Formation, SCPs.
  • SCT for schema and code, DMS for data. Migration between engines usually needs both.
  • Inmon and data vault are possible in Redshift but need extra work. Supported directly: star, snowflake, Kimball.

Lesson 1: Automate data processing by using AWS services

Infrastructure as code and CI/CD

  • A CloudFormation template can create the whole pipeline: S3 bucket, EventBridge rule, Lambda, SNS topic, Step Functions, Glue job, Glue crawler.
  • Example flow: a file lands in S3, EventBridge triggers a validation Lambda, Lambda starts the state machine, the state machine runs a Glue job, then a Glue crawler updates the Data Catalog. SNS sends a notification on failure.
  • Store templates in S3 or CodeCommit for access and versioning.
  • CodePipeline automates CI/CD. Committing a Python file to CodeCommit triggers CodeBuild for build, integration, and unit tests.
  • Continuous delivery adds end-to-end tests: ingest a file, run the transformation, validate the output.
  • Note: CodeCommit has been closed to new customers since July 2024, but it can still show up in questions.

Orchestration: Amazon MWAA vs Step Functions

  • Amazon MWAA is managed Apache Airflow. Workflows are written as DAGs of tasks with dependencies (Spark job, Glue job, AWS Batch job).
  • Step Functions is a serverless service built on state machines. Each state can run a task, make a decision, or wait for an event.
  • Step Functions has built-in error handling, retries, and workflow visualization.
  • MWAA fits complex, flexible, code-based workflows. Step Functions fits serverless, event-driven workflows with AWS services.

Troubleshooting MWAA

  • Check CloudWatch Logs for errors and exceptions, then the Apache Airflow logs themselves.
  • Check IAM roles and permissions for MWAA, the DAGs, and related services (Glue, S3, EMR).
  • Make sure DAG dependencies and file references are correct, and external services are reachable from the MWAA environment.
  • Adjust worker node count and size to avoid out-of-memory errors.
  • Test DAGs locally or in a test environment first, and use the latest Airflow and plugin versions.

Consume and maintain data APIs

  • Lambda calls APIs and processes responses, triggered by events or API Gateway.
  • API Gateway gives a managed endpoint for external clients and can act as a frontend for Lambda.
  • The AWS SDK handles authentication, request signing, and response parsing.
  • Monitor error rate and latency with CloudWatch.
  • Caching with API Gateway caching or ElastiCache. Throttling and rate limiting in API Gateway prevent abuse.
  • Secure with IAM and OAuth. API versioning keeps backward compatibility. Lambda layers manage dependencies and shrink the package.

Queries and events

  • Athena fits quick exploration with no infrastructure setup and pay per query. Results can be downloaded or saved to S3.
  • An EventBridge rule matches events by pattern (attributes, custom event bus), then sends them to one or more targets.
  • API calls to EventBridge are logged by CloudTrail. EventBridge schema registry is an optional feature for managing event schemas.
  • Step Functions example: a Lambda checks the file extension, a Choice state decides. Supported files go to a second Lambda, unsupported files trigger an SNS notification.
  • CloudTrail does not log S3 object-level data events by default. Create a trail that logs both management and data events.
  • An EventBridge rule with service S3, specific operations and bucket, and a state machine target starts the workflow when a file arrives.

Lesson 2: Analyze data by using AWS services

Data manipulation operations

  • Aggregation summarizes many records into one value: Redshift (sum, average, count), Athena (GROUP BY), OpenSearch Service (date histogram, term aggregation).
  • Rolling average computes the average over a window to smooth out fluctuations: Redshift (AVG window function) and QuickSight (moving calculation).
  • Grouping: Redshift and Athena (GROUP BY), QuickSight (dimensions and aggregations).
  • Pivoting turns rows into columns: Redshift (PIVOT clause) and QuickSight (pivot table).

Services for data consumers

  • QuickSight: interactive dashboards and ad hoc analysis.
  • AWS Glue DataBrew: visual data preparation with no code.
  • Athena: SQL on S3 data. Redshift: SQL for large datasets. EMR: Spark and Hadoop.
  • AWS Glue: discover, catalog, transform, and automatically generate ETL code.
  • AWS Data Pipeline: data orchestration across AWS services and on premises. Note: Data Pipeline is in maintenance mode and does not accept new customers.
  • Lake Formation: secure access to data from many sources in a data lake.

Example scenarios

  • A script on EC2 cleans S3 data into CSV for spreadsheets every 8 hours, then dashboards and search are needed. Solution: move to Lambda, send results to OpenSearch, trigger with EventBridge every 8 hours.
  • IoT sensor data with cost-effective daily visual reports: an EMR transient cluster aggregates every night then terminates automatically, reports in QuickSight.
  • EMR has two cluster types: transient and persistent.

SQL across services

  • SQL syntax is consistent even though each service runs it differently. RDS and Aurora use SQL for CRUD.
  • DynamoDB supports PartiQL, a SQL-compatible query language for structured, semi-structured, nested, and schemaless data.
  • Amazon DocumentDB is MongoDB compatible and can use SQL-like queries.
  • Athena can run Spark applications through Python or the Athena notebook APIs. EMR provides Jupyter Notebook for Spark code.

Data verification and cleaning

  • Lambda for custom validation and enrichment. Athena for SQL-based verification.
  • QuickSight for visual exploration. Jupyter Notebooks for complex cleaning.
  • SageMaker Data Wrangler to prepare data for ML models.
  • One workflow commonly uses several services together.

Lesson 3: Maintain and monitor data pipelines

Monitoring and observability

  • Data side: check inputs, outputs, and schema. Run quality tests on inputs and transformation results so you can flag issues, roll back, and find the root cause.
  • Operational metrics: query queue length, query concurrency, memory usage, storage utilization, network latency, disk I/O.
  • Refactor slow queries. If the query is already good, tune the database (cluster or cache tables) or scale up compute.
  • Tools: CloudWatch, X-Ray, CloudWatch Logs Insights, GuardDuty, Inspector, Security Hub. Applications must be instrumented for traces, metrics, and logs.

Logging application data

  • CloudWatch Logs stores logs and sends notifications when a threshold is reached.
  • CloudWatch Events delivers system events in near real time using rules. Note: CloudWatch Events is now part of EventBridge.
  • EventBridge routes events from your own apps, SaaS, and AWS services to targets such as Lambda.
  • X-Ray gives end-to-end tracing for distributed applications and microservices.
  • Lambda logs every invocation automatically. ALB access logs record request time, client IP, user agent.
  • RDS has an error log, slow query log, and general log.
  • A log group is a container for log streams. It can be created with CloudFormation. CloudWatch Logs default retention is forever, so set a retention policy for cost and retention rules.

Traceability and audit

  • CloudTrail records every API call: who, what, when. Logs go to S3 or CloudWatch Logs.
  • AWS Config records resource configuration history. AWS Managed Rules assess compliance against best practices.
  • CloudFormation StackSets deploy CloudTrail, CloudWatch, and Config configuration across many accounts and Regions.
  • VPC Flow Logs capture IP traffic for network interfaces in a VPC.
  • Security Hub combines GuardDuty, Inspector, and Config findings in one dashboard.
  • Macie sends policy findings and sensitive data findings to EventBridge as events, and to Security Hub if publication settings are configured. Macie does not send logs to CloudWatch Logs.

Performance troubleshooting

  • Compare CPU, memory, network, disk I/O, and database performance against a baseline.
  • Check the AWS Health Dashboard first before debugging the application.
  • Read application logs in CloudWatch Logs, then the specific Lambda, RDS, or EC2 logs.
  • VPC Flow Logs and Network Load Balancer access logs help spot latency and packet loss.
  • Case: Kinesis Data Streams with 40 shards, KCL consumers in an Auto Scaling group, results to DynamoDB: CPU below 35 percent and no ProvisionedThroughputExceededException. So increase DynamoDB write capacity.
  • Redshift with long running queries: configure scaling on workload management (WLM) queues through the parameter group, so short queries do not wait in line.

Error handling per service

  • Managed services handle many errors themselves. In EMR and Kinesis Data Streams, you program the error behavior yourself.
  • New Hadoop application on EMR: enable debugging, test with a small representative subset of data, run steps one at a time.
  • Kinesis Data Streams: producer issues (cannot connect, slow writes) and consumer issues (record problems, slow reads).
  • Managed Service for Apache Flink: common issues are stream access, lost data, processing failures, application errors. Investigate through CloudWatch Logs.
  • Flink can detect anomalies with random cut forest, then Lambda takes action. Note: RANDOM_CUT_FOREST comes from Kinesis Data Analytics for SQL, which AWS has discontinued.
  • Firehose retries until the retry duration runs out, then backs up to the S3 backup bucket. If the S3 destination or S3 backup fails, it retries until the retention period runs out. Note: it is now called Amazon Data Firehose.

Lesson 4: Ensure data quality

Principles

  • Consumers must trust the data. Work backwards from the customer: who uses it, how it is used, what they need.
  • Publishing no data is better than publishing bad data. Automated checks must be able to stop the pipeline.
  • Duplicates in a primary key column: send a notification. The process does not always have to stop completely.
  • Place checks before, during, and after transformation. Too many checks cause false positives, too few let problems through.

Data profiling and validation

  • Profiling looks at nulls, distribution, anomalies, cardinality, relationships between fields, and statistics (min, max, mean, median, standard deviation).
  • DataBrew builds profiles with no code. Athena and Redshift for profiling with SQL. EMR Spark for custom scripts. There are also tools in AWS Marketplace.
  • Validation has four dimensions: completeness, consistency, accuracy, integrity.
  • Checks during processing: DataBrew recipes for empty fields, formats, and uniqueness. EMR Spark for custom checks.
  • Lambda for complex checks and remediation, Step Functions for orchestration based on validation results. Data Wrangler for missing values and duplicates.

Duplicates in Redshift

  • Case: CSV in S3, a Glue crawler fills the Data Catalog, a Glue job writes to Redshift, then duplicates appear after a rerun.
  • Solution: the Glue job writes to a staging table, then replaces existing rows in the target before the new data is stored.
  • Merge: join the staging table with the target, then update and insert. An upsert through the Glue job removes duplicates.

Data sampling

  • S3 Select pulls a subset of data from an S3 object with SQL-like queries. Note: S3 Select is not available to new customers since July 2024.
  • Athena and Redshift: LIMIT clause.
  • EMR Spark: systematic, random, or stratified sampling.
  • Data Wrangler: sampling for balanced datasets. DataBrew: filter a subset through transformations.

Data skew

  • Data skew is uneven distribution across partitions or nodes, which creates bottlenecks.
  • Detection: CloudWatch custom metrics (records per partition or key, processing time) with threshold alarms.
  • Glue ETL: CloudWatch metrics and Glue job bookmarks, which make the job resume from the last processed record.
  • EMR Spark: detailed logging to CloudWatch Logs, look for long tasks, uneven task distribution, skewed partitions. Real time: Spark Streaming with Kinesis or Kafka.
  • Handling: partitioning keys with a hash function, load balancing, replicating hotspot data, shuffling, dynamic repartitioning.
  • Skew joins: bloom filter or skew join algorithm. EMR has automatic skew join optimization. Redshift has adaptive join (hash join or sort merge join).
  • Pre-processing (data binning, feature scaling, log transformation) and smaller tasks help even out the load.

Partitioning and bucketing in Athena

  • Common strategy: partition by date (year, month, day). A WHERE filter on partition columns reads only the matching S3 prefixes.
  • Partitioning and bucketing both reduce the data Athena scans.
  • A bucket here is not an S3 bucket. A bucket is a file, a hash function decides each record's bucket, and the bucket number is in the file name.
  • Engine v2 supports Hive bucketing. Engine v3 also supports Spark bucketing. Default is Hive. For Spark, set bucketing_format to spark in TBLPROPERTIES.

Redshift Spectrum and DataBrew rules

  • Join historical data in S3 (registered in the Data Catalog) with Redshift tables: Redshift Spectrum external table, then join with SQL.
  • DataBrew rules: completeness (nulls), format (email, phone number), range (numeric ranges), uniqueness (duplicates).
  • DataBrew flags records that fail, gives statistics and visualizations, and can be automated.

Lesson 1: Apply authentication mechanisms

Identity in AWS

  • Authentication confirms who you are. Authorization decides what you can access after that.
  • Methods: password-based, certificate-based, role-based. Know their use cases and security level.
  • Ways to sign in: root user, IAM user, assume an IAM role, or federated identity.
  • IAM Identity Center: workforce sign-in, multi-account access, and SSO to SAML 2.0 applications.
  • IAM user is for one person or application, with permanent credentials. An IAM role can be assumed by anyone who needs it, with temporary credentials.
  • You cannot sign in as an IAM group. Groups only grant permissions to many users.
  • A service calls another service using the calling principal's permissions, a service role, or a service-linked role.

Policies

  • Types: identity-based (attached to users, groups, roles), resource-based (attached to resources such as an S3 bucket or KMS key), and trust policies.
  • An IAM role needs two policies: a trust policy (who can assume it) and an identity-based policy (what it can do).
  • Without an explicit allow, the AWS default is deny.
  • AWS managed policies are maintained by AWS and cannot be changed. Customer managed policies are your own and can be attached to many identities.
  • An inline policy is one to one with an identity and is deleted when the identity is deleted.

Policies on endpoints and services

  • Access through an S3 access point works only if both the access point policy and the bucket policy allow it. Or the bucket delegates access control to the access point.
  • Users have no permission to manage VPC endpoints by default. The condition key ec2:VpceServicePrivateDnsName restricts endpoints by private DNS name.
  • API Gateway has two permission models: API management (developers) and API execution (callers). Set the method authorization type to AWS_IAM so callers must send credentials.
  • API Gateway to Lambda: an IAM role with a trust policy for API Gateway plus the lambda:InvokeFunction permission.
  • An interface VPC endpoint to CloudFormation can have an endpoint policy, for example to deny creating stacks through that endpoint.

Network, certificates, secrets

  • Network protection: security groups, network ACLs, private subnets, bastion hosts, NAT gateways, route tables, AWS VPN, Direct Connect, VPC Flow Logs, Security Hub, Network Firewall.
  • ACM creates, stores, and renews SSL/TLS X.509 certificates. You can import third-party certificates, or export AWS Private CA certificates for internal PKI.
  • Secret lifecycle: create, store, use, destroy.
  • Secrets Manager integrates with IAM (including resource-based policies on secrets) and KMS (AWS managed key or customer managed key).
  • Scheduled automatic rotation for RDS, Redshift, DocumentDB. Other secrets (API keys, OAuth tokens) use a custom Lambda function.

Lesson 2: Apply authorization mechanisms

Principles

  • The goal is least privilege for authenticated principals.
  • Policies can be built and tested as code in a pipeline.
  • IAM Access Analyzer continuously looks for resources that can be accessed from outside the account. AWS Organizations enforces policies across many accounts.

RBAC and ABAC

  • RBAC: access based on roles. Easier to manage.
  • ABAC: access based on attributes and tags on the principal, resource, environment, or application state.
  • Choose ABAC when users need permissions across roles, roles are hard to define, or permissions depend on dynamic parameters.
  • Example: roles tagged access-project heart, star, bolt. One policy grants access when the role tag matches the resource tag.
  • ABAC is granular but takes more work up front. The two can be combined (hybrid).

Amazon Redshift

  • Users are managed with CREATE USER and ALTER USER, or through a JDBC/ODBC driver that creates a temporary password.
  • Only a superuser can create and drop users. A superuser has owner rights on all databases.
  • With RBAC, grants and revokes happen at the role level, without changing each object's permissions.

Lake Formation and Parameter Store

  • Lake Formation controls data lake access down to database, table, column, row, and cell level, for IAM and external identity providers.
  • It applies when data is accessed through Redshift Spectrum, Athena, Glue ETL, and EMR for Spark.
  • LF-Tags are attached to databases, tables, or columns, replacing thousands of permission definitions with a few tags.
  • Lake Formation can manage Redshift datashare permissions centrally.
  • Parameter Store (Systems Manager) stores configuration and secrets, but has no automatic rotation. Store secrets in Secrets Manager and reference them from Parameter Store, with the name starting with /.

Lesson 3: Ensure data encryption and masking

KMS, CloudHSM, TLS

  • AWS KMS creates and controls keys, integrates with almost every service, and with CloudTrail to log key usage.
  • Use CloudHSM when you must manage the HSM devices directly. AWS handles hardware, patching, and backups. You handle scaling plus crypto accounts and credentials.
  • In KMS and CloudHSM, plaintext keys cannot be used outside the HSM.
  • Traffic between data centers is encrypted at the physical layer. Traffic within a VPC and between peered VPCs across Regions is encrypted at the network layer. All AWS endpoints support TLS.
  • TLS termination with your own certificates: NLB, ALB, CloudFront, API Gateway.
  • Note: the transcript says "hardware security models", meaning hardware security modules.

Encryption at rest and EMR

  • Know encryption at rest for EBS, S3, RDS, Redshift, ElastiCache, Lambda, EMR, Glue, SageMaker. SQS has SSE for sensitive messages.
  • Know the difference between client-side and server-side encryption.
  • Encrypted EBS on EMR does not mean the local disks are encrypted. Turn on local disk encryption in the security configuration.
  • EBS encryption happens on the EC2 host. The OS sees unencrypted data unless there is end-to-end encryption.
  • Encrypted root volumes on all EMR nodes: custom AMI. Copy the snapshot to a KMS-encrypted target, then use the custom AMI ID in the CloudFormation template.

Tokenization, masking, salt

  • Encryption uses an algorithm and a key, and can be decrypted. Tokenization replaces data with a random token without a mathematical process, and the mapping is kept in a token vault.
  • Tokens cannot be mapped back without the tokenization system. Example: recurring credit card payments.
  • Anonymization removes sensitive data. Masking hides it with altered values.
  • Salt: new random data per password, combined and then hashed, stored with the hash. The salt does not need to be encrypted.
  • Serverless tokenization example: Cognito, API Gateway, Lambda, KMS, DynamoDB client-side encryption library, a cipher database and an application database. Lambda reaches DynamoDB through a gateway endpoint and KMS through an interface endpoint.
  • Redshift Dynamic Data Masking (DDM) masks data at query time without changing stored data. It can work per role, per cell with conditional columns, and with several policies on one column.

Lesson 4: Prepare logs for audit

Retention and CloudTrail Lake

  • HIPAA and PCI require data to be kept for a set period, be searchable, and then be deleted according to the rules.
  • CloudWatch Logs keeps logs forever by default. Set a retention policy on the log group.
  • CloudTrail Lake: central SQL queries over events across accounts and Regions, including activity from outside AWS.
  • An event data store holds one category only: CloudTrail events, Config configuration items, Audit Manager evidence, or events from outside AWS. Combine them with SQL JOIN.
  • Trails do not support tag-based authorization, event data stores do.

EMR and log analysis

  • EMR writes logs on the primary node, /mnt/var/log/, and can archive them to S3.
  • CloudTrail records all EMR API calls. A trail delivers continuously to S3. Without a trail, only recent events in Event history.
  • CloudWatch Logs Insights to find the cause of problems. Fields are discovered automatically for Route 53, Lambda, CloudTrail, VPC, and JSON logs.
  • Athena CloudWatch connector: log groups become schemas, log streams become tables, the all_log_streams view covers all streams.
  • Log groups can be streamed to OpenSearch Service in near real time through a subscription.
  • Note: CloudWatch Events is now part of Amazon EventBridge.

Lesson 5: Understand data privacy and governance

Protection across the lifecycle

  • Field-level encryption encrypts only sensitive fields and keeps the payload structure. Full payload encryption makes the payload unusable until it is all decrypted.
  • Protect data as early as possible at ingestion. CloudFront plus Lambda@Edge protects data at the edge so downstream systems never see it.
  • Example pipeline: IoT Core (MQTT), Kinesis Data Firehose to S3, Glue ETL calling Amazon Comprehend to detect sensitive data, Lake Formation restricting analyst access in Athena.
  • Note: Kinesis Data Firehose is now called Amazon Data Firehose.

Sensitive data discovery

  • Scheduled scans (default four times a day, every 6 hours), before the crawler and after redaction or tokenization.
  • Scanning adds at least 5 to 10 minutes, growing linearly with object size, plus a constant startup time per job.
  • Components: raw, scanning, manual review, and scanned buckets. Macie scans, Step Functions orchestrates Lambda, EventBridge triggers the schedule, SNS sends notifications, API Gateway receives the reviewer's decision.
  • What is missing: a backup plan, a DR plan, and a data privacy strategy so backups or replication do not go to a prohibited Region (data sovereignty).

Data lake backup

  • Storage admins use S3 versioning, Same-Region Replication, Cross-Region Replication, and Object Lock.
  • AWS Backup creates backup plans (frequency, retention) in one account or many accounts through Organizations. A backup vault has its own policy, key, and lock.
  • Backing up the raw bucket is usually enough because derived data can be rebuilt. If raw holds PII, back up de-identified data.
  • Select buckets by tag, for example "data protection level" = "critical".
  • Continuous backup for PITR, periodic for compliance. Copy to destination sends to a vault in another account or Region. Encryption uses the vault's KMS key.
  • AWS Backup Audit Manager reports backup compliance through custom frameworks.

Redshift and AWS Config

  • A Redshift user cannot be dropped while it still owns or has permissions on datashare objects.
  • Confidential columns in a Redshift table: column-level GRANT and REVOKE. Lake Formation plus Redshift Spectrum also works.
  • AWS Config records a configuration item for each resource through describe or list API calls, including related resources (example: change a security group and the related instances are recorded too).
  • Items are delivered through the configuration stream to S3. Each Config rule uses a Lambda function. Notifications can go to SNS.

Key numbers and limits

  • Domain 4 has five task statements.
  • Secret lifecycle: four phases.
  • Built-in Secrets Manager rotation: RDS, Redshift, DocumentDB.
  • An IAM role needs two policies.
  • Lake Formation control levels: database, table, column, row, cell.
  • Layers between the OS and EBS: three (local disk, EBS volume, volume presented to the VM).
  • CloudWatch Logs default retention is unlimited.
  • EMR default logs: primary node, /mnt/var/log/.
  • CloudTrail Lake: one event data store per category. CloudWatch metrics show data ingested during the last hour or over the retention period.
  • Sensitive data scan: default every 6 hours (four times a day), adds at least 5 to 10 minutes.
  • Referencing Secrets Manager from Parameter Store: name starts with /.

Exam traps

  • Authentication and authorization are often swapped.
  • IAM user has permanent credentials, IAM role has temporary credentials.
  • AWS managed policies cannot be edited. Reusable custom permissions: customer managed policy, not inline.
  • An access point policy alone is not enough, the bucket policy must also allow.
  • User permissions do not automatically apply to services. QuickSight needs its own permission to S3.
  • Parameter Store has no automatic rotation, Secrets Manager does.
  • KMS and CloudHSM look similar. CloudHSM only when the question asks for direct control over the HSM.
  • Encrypted EBS on EMR does not encrypt the local disks.
  • Tokenization is not encryption, there is no mathematical process.
  • Anonymization removes, masking hides. Salt does not need to be encrypted.
  • Redshift DDM does not change stored data.
  • CloudTrail trails do not support tag authorization, CloudTrail Lake event data stores do.
  • Without a trail, CloudTrail does not deliver events to S3, only recent Event history.
  • Backup vaults are separate from S3 Object Lock and bucket policies.
